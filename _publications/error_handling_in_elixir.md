## Սխալների և բացառությունների մշակումը Elixir-ում

[Նախորդ հոդվածում](./error_handling_approaches.md) դիտարկեցինք, թե տարբեր ծրագրավորման լեզուներում սխալներն ինչպես են ներկայացվում և մշակվում։ Այժմ կկենտրոնանանք Elixir-ի վրա։

Elixir-ում սխալների մշակման համար հատկապես կարևոր է տարբերել երկու իրավիճակ․

* գործողությունը կարող է ձախողվել ծրագրի բնականոն աշխատանքի ընթացքում,
* տեղի է ունեցել անսպասելի կամ բացառիկ իրադարձություն, և ծրագրի աշխատանքը չի կարող շարունակվել սովորական ձևով։

Առաջին դեպքում ձախողումը հաճախ ներկայացվում է որպես սովորական արժեք՝ `{:error, reason}`։ Երկրորդ դեպքում առաջանում է բացառություն։ Այս տարբերակումը հասկանալը շատ ավելի կարևոր է, քան պարզապես `try` և `rescue` կառուցվածքների գրելաձևը հիշելը։

### Սպասելի ձախողումը որպես արժեք

Elixir-ում ֆունկցիաները հաճախ հաջող արդյունքը վերադարձնում են `{:ok, result}`, իսկ սպասելի ձախողումը՝ `{:error, reason}` տեսքով։ Երկու արդյունքն էլ սովորական արժեքներ են, ուստի դրանք կարելի է մշակել pattern matching-ի միջոցով։

Պատկերացնենք ապրանքների քանակ ամրագրող ֆունկցիա․

```elixir
defmodule Inventory do
  def reserve(available, requested)
      when is_integer(available) and available >= 0 and
             is_integer(requested) and requested > 0 do
    if requested <= available do
      {:ok, available - requested}
    else
      {:error, :not_enough_items}
    end
  end

  def reserve(_available, _requested), do: {:error, :invalid_quantity}
end
```

Ֆունկցիան կարող է վերադարձնել երեք տարբեր արդյունք․

```elixir
iex> Inventory.reserve(10, 3)
{:ok, 7}

iex> Inventory.reserve(10, 12)
{:error, :not_enough_items}

iex> Inventory.reserve(10, 0)
{:error, :invalid_quantity}
```

Պահեստում անհրաժեշտ քանակի բացակայությունը ծրագրավորման սխալ չէ։ Այն ծրագրի բիզնես տրամաբանությամբ սպասելի արդյունք է, որի դեպքում կանչող կոդը պետք է որոշի հետագա քայլը։ Օրինակ՝

```elixir
case Inventory.reserve(10, 12) do
  {:ok, remaining} ->
    "Reservation succeeded, #{remaining} items left"

  {:error, :not_enough_items} ->
    "Not enough items in stock"

  {:error, :invalid_quantity} ->
    "Invalid quantity"
end
```

Այս մոտեցման դեպքում ֆունկցիան չի որոշում, թե օգտատիրոջն ինչ հաղորդագրություն ցույց տալ կամ արդյոք պետք է կրկին փորձել։ Այն վերադարձնում է անհրաժեշտ տեղեկությունը, իսկ համապատասխան որոշումն ընդունում է կանչող կոդը։

### Սովորական և `!`-ով ավարտվող ֆունկցիաներ

Elixir-ի ստանդարտ գրադարանում հաճախ նույն գործողության համար կան երկու ֆունկցիաներ։ Սովորական տարբերակը վերադարձնում է հաջողության կամ ձախողման մասին արժեք, իսկ `!`-ով ավարտվող տարբերակը ձախողման դեպքում առաջացնում է բացառություն։

Օրինակ՝ `File.read/1` ֆունկցիան վերադարձնում է tuple․

```elixir
iex> File.read("settings.txt")
{:ok, "..."}

iex> File.read("missing.txt")
{:error, :enoent}
```

Այդ արդյունքը կարելի է օրինակ հետևյալ ձևով մշակել․

```elixir
case File.read("settings.txt") do
  {:ok, content} ->
    IO.puts(content)

  {:error, reason} ->
    IO.puts("Could not read the file: #{reason}")
end
```

Իսկ `File.read!/1`-ը հաջողության դեպքում անմիջապես վերադարձնում է ֆայլի պարունակությունը, բայց ձախողման դեպքում առաջացնում է `File.Error` բացառություն․

```elixir
content = File.read!("settings.txt")
```

Ֆունկցիայի անվան վերջում գրված `!` նշանը լեզվական շարահյուսության մաս չէ և ինքնին չի նշանակում «վտանգավոր»։ Այն ընդամենը պայմանավորվածություն է։ Սովորաբար այդպիսի ֆունկցիան վերադարձնում է անմիջական արդյունք կամ առաջացնում բացառություն։

Ընտրությունը կախված է համատեքստից։ Եթե ֆայլի բացակայությունը սպասելի է, `File.read/1`-ը հնարավորություն է տալիս արձագանքել դրան։ Եթե ծրագրի աշխատանքի համար ֆայլը պարտադիր է, և առանց դրա շարունակել հնարավոր չէ, `File.read!/1`-ի օհտագործումը կարող է ավելի արտահայտիչ և արդարացված որոշում լինել։

### Ի՞նչ է բացառությունը Elixir-ում

Elixir-ում յուրաքանչյուր բացառություն struct է, որի module-ը իրականացնում է Exception behaviour-ը։ Այն պահում է սխալի տեսակի մասին տեղեկություն և սխալը նկարագրող հաղորդագրություն։ Երբ բացառություն է առաջանում, ֆունկցիայի սովորական կատարումն ընդհատվում է, և բացառությունը փոխանցվում է կանչերի շղթայով վերև, մինչև մշակվի։ Եթե բացառությունը ոչ մի տեղ չի մշակվում, տվյալ գործողության կատարումն ավարտվում է սխալով։

Elixir-ում հաճախ հանդիպող բացառություններից են՝

* `ArgumentError`՝ ֆունկցիային անթույլատրելի արգումենտ փոխանցելու դեպքում,
* `ArithmeticError`՝ թվաբանական անթույլատրելի գործողության դեպքում,
* `KeyError` երբ տվյալների կառուցվածքում չի գտնվում պահանջվող բանալին
* `MatchError`՝ `=` օպերատորով անհաջող pattern matching-ի դեպքում,
* `FunctionClauseError`՝ երբ ֆունկցիայի ոչ մի clause չի համապատասխանում արգումենտներին,
* `File.Error`՝ ֆայլային գործողության ձախողման դեպքում,
* `RuntimeError`՝ ընդհանուր նշանակության runtime բացառություն։

Օրինակ՝ թիվը atom-ին գումարել հնարավոր չէ․

```elixir
iex> :foo + 1
** (ArithmeticError) bad argument in arithmetic expression
```
Գործողությունն ինքնին անթույլատրելի է և սովորաբար վկայում է ծրագրավորման սխալի մասին։

### Բացառության առաջացումը `raise`-ով

Կոդում բացառություն առաջացնելու համար օգտագործվում է raise-ը։ Օրինակ՝ ֆունկցիան կարող է պահանջել, որ քաշը լինի դրական թիվ․

```elixir
defmodule Shipping do
  def cost(weight) when is_number(weight) and weight > 0 do
    weight * 500
  end

  def cost(_weight) do
    raise ArgumentError, message: "weight must be a positive number"
  end
end
```

Թույլատրելի արժեքի դեպքում ֆունկցիան վերադարձնում է արդյունքը․

```elixir
iex> Shipping.cost(2)
1000
```

Իսկ ֆունկցիայի պայմանագիրը խախտող արգումենտի դեպքում առաջանում է `ArgumentError`․

```elixir
iex> Shipping.cost(-2)
** (ArgumentError) weight must be a positive number
```

Սակայն `raise`-ը մուտքային տվյալների բոլոր սխալների համար ընդհանուր լուծում չէ։ Եթե բացասական քաշը, օրինակ, օգտատիրոջ լրացրած ձևի սպասելի սխալ է, ավելի հարմար կարող է լինել `{:error, :invalid_weight}` վերադարձնելը։ Որոշում կայացնելու համար կարևոր է հասկանալ համատեքստը։

`raise "message"` կարճ գրելաձևն ուղղակի ստեղծում է `RuntimeError`։ Երբ սխալի համար կա ավելի ճշգրիտ տեսակ, նախընտրելի է օգտագործել այն։

### Բացառության մշակումը `try/rescue`-ով

`try/rescue` կառուցվածքը հնարավորություն է տալիս մշակել բացառությունները․

```elixir
defmodule Port do
  def parse(text) do
    try do
      {:ok, String.to_integer(text)}
    rescue
      ArgumentError -> {:error, :invalid_port}
    end
  end
end
```

```elixir
iex> Port.parse("4000")
{:ok, 4000}

iex> Port.parse("four thousand")
{:error, :invalid_port}
```

`String.to_integer/1`-ը անթույլատրելի արժեքի դեպքում առաջացնում է `ArgumentError`, իսկ `rescue` ճյուղն այստեղ այն վերածում է սովորական սխալի արժեքի։ `try/rescue`-ն արտահայտություն է, հետևաբար ամբողջ կառուցվածքի արդյունքը կատարված ճյուղի վերջին արտահայտության արժեքն է։

Օրինակը զուտ գրելաձևը պարզ բացատրելու համար է, տվյալ խնդիրը կարելի է լուծել նաև առանց բացառության․

```elixir
defmodule Port do
  def parse(text) do
    case Integer.parse(text) do
      {port, ""} when port in 1..65_535 -> {:ok, port}
      _other -> {:error, :invalid_port}
    end
  end
end
```

Երկրորդ տարբերակից անմիջապես երևում է, որ անթույլատրելի մուտքային արժեքը ֆունկցիայի սպասելի արդյունքներից մեկն է։ Elixir-ում try/rescue-ի կարիք համեմատաբար հազվադեպ է լինում։ Այն սովորաբար կիրառվում է, երբ կանչվող API-ը ձախողման դեպքում բացառություն է առաջացնում, իսկ տվյալ կոդը գիտի՝ ինչպես մշակել այդ իրավիճակը կամ այն ներկայացնել {:error, reason} արժեքով։

rescue ճյուղում պետք է նշել միայն այն բացառությունները, որոնք տվյալ կոդը կարող է ճիշտ մշակել։ Բոլոր բացառությունները մշակող ընդհանուր ճյուղը կարող է թաքցնել ծրագրավորման սխալները, և ծրագիրը կշարունակի աշխատել սխալ վիճակում։ Եթե տվյալ հատվածը չի կարող լուծել խնդիրը կամ վերադարձնել օգտակար արդյունք, բացառությունը մշակելու կարիք չկա․ այն պետք է փոխանցվի կանչող կոդին։

### Սեփական բացառության սահմանումը

Ծրագրին հատուկ բացառություն կարելի է սահմանել `defexception`-ով․

```elixir
defmodule InvalidOrderError do
  defexception message: "order is invalid"
end
```

Այնուհետև հնարավոր է առաջացնել այդ բացառությունը և փոխել նախնական հաղորդագրությունը․

```elixir
raise InvalidOrderError,
  message: "order must contain at least one item"
```

```text
** (InvalidOrderError) order must contain at least one item
```

Սեփական բացառությունը օգտակար է, երբ ծրագիրը պետք է տարբերակի տվյալ տիրույթին հատուկ բացառիկ պայմանը ընդհանուր `RuntimeError`-ից կամ այլ սխալներից։ Սակայն յուրաքանչյուր `{:error, reason}` արժեքի համար առանձին exception module ստեղծելու կարիք չկա։ Սպասելի ձախողումները շարունակում են մնալ սովորական արժեքներ։

### Մաքրող գործողությունները `after`-ով

Երբ կոդը բացում կամ զբաղեցնում է որևէ ռեսուրս, այն երբեմն պետք է ազատել նաև բացառության դեպքում։ `try/after` կառուցվածքը նախատեսված է այդպիսի մաքրող գործողությունների համար․

```elixir
{:ok, file} = File.open("events.log", [:append, :utf8])

try do
  IO.write(file, "started\n")
after
  File.close(file)
end
```

`after` ճյուղը կատարվում է թե՛ `try` բլոկի սովորական ավարտից, թե՛ այնտեղ բացառություն առաջանալուց հետո։ Այն չի մշակում բացառությունը։ `File.close/1`-ի կատարումից հետո սկզբնական արդյունքը վերադարձվում է կամ առաջացած բացառությունը փոխանցվում է կանչող կոդին։

try/after-ը պետք է օգտագործել, երբ զբաղեցրած ռեսուրսն աշխատանքից հետո անհրաժեշտ է անպայման ազատել։ Սակայն որոշ API-ներ ռեսուրսն իրենք են բացում և փակում՝ ընդունելով կատարվող ֆունկցիան որպես արգումենտ։ Այդպիսի API-ի առկայության դեպքում ավելի լավ է օգտագործել այն

### `throw`, `exit` և «թող խափանվի» գաղափարը

Elixir-ում raise-ով առաջացած բացառությունները մշակվում են try/rescue-ով։ Լեզուն ունի նաև throw/catch, սակայն այն JS-ի կամ Java֊ի try/catch-ի համարժեքը չէ և սովորական բացառությունների մշակման համար չի օգտագործվում։ exit-ը կապված է process-ների աշխատանքի ավարտի հետ։ Այս մեխանիզմներին ավելի մանրամասն կանդրադառնանք համապատասխան թեմաներն ուսումնասիրելիս։

Erlang և Elixir համայնքներում տարածված «թող խափանվի» (`let it crash`) սկզբունքը նույնպես չի նշանակում անտեսել սպասելի սխալները կամ յուրաքանչյուր խնդրի դեպքում դադարեցնել ծրագիրը։ Այն վերաբերում է անսպասելի խափանումները մեկուսացված process-ում թաքցնելու փոխարեն այդ process-ի ավարտին և վերահսկվող վերականգնմանը։ Այս գաղափարը հնարավոր է ճիշտ հասկանալ միայն process-ները ուսումնասիրելուց հետո։ Process-ների խափանումներին, `exit` ազդանշաններին, կապերին, monitor-ներին և supervision-ին կանդրադառնանք համապատասխան թեմաներից հետո՝ առանձին հոդվածում։

### Ինչպե՞ս ընտրել մոտեցումը

Գործնականում կարելի է հերթով տալ հետևյալ հարցերը․

1. **Արդյո՞ք ձախողումը գործողության սպասելի արդյունք է։** Վերադարձրեք `{:ok, result}` կամ `{:error, reason}` և մշակեք այն pattern matching-ով։
2. **Խախտվե՞լ է ֆունկցիայի պայմանագիրը կամ առաջացե՞լ է անսպասելի վիճակ։** Առաջացրեք համապատասխան բացառություն կամ թույլ տվեք արդեն առաջացած բացառությանը փոխանցվել վերև։
3. **Կարո՞ղ է ընթացիկ կոդն իմաստալից վերականգնվել կանչվող API-ի առաջացրած բացառությունից։** Մշակեք միայն անհրաժեշտ բացառությունը `try/rescue`-ով։
4. **Պե՞տք է անպայման ազատել զբաղեցրած ռեսուրսը։** Օգտագործեք համապատասխան API կամ անհրաժեշտության դեպքում `try/after`։

Բացառությունը չպետք է օգտագործել որպես սովորական պայմանական ճյուղավորման փոխարինում։ Բացառությունը պետք չէ մշակել միայն այն բանի համար, որ ծրագիրը ցանկացած գնով շարունակի աշխատանքը։ Սխալը պետք է մշակել այն մակարդակում, որն ունի բավարար տեղեկություն իմաստալից որոշում ընդունելու համար։

### Ամփոփում

Elixir-ը սպասելի ձախողումների և բացառիկ իրավիճակների համար առաջարկում է տարբեր միջոցներ․

* `{:ok, result}` և `{:error, reason}` արժեքները հարմար են սպասելի արդյունքների համար,
* `!`-ով ավարտվող ֆունկցիաները սովորաբար վերադարձնում են անմիջական արդյունք կամ առաջացնում բացառություն,
* `raise`-ը բացահայտ առաջացնում է բացառություն,
* `try/rescue`-ը մշակում է ընտրված բացառությունը, բայց Elixir-ում այն համեմատաբար հազվադեպ է անհրաժեշտ,
* `defexception`-ը սահմանում է ծրագրին հատուկ բացառություն,
* `try/after`-ը թույլ է տալիս կատարել անհրաժեշտ մաքրող գործողությունը՝ առանց բացառությունը թաքցնելու։

Հիմնական ընտրությունը գրելաձևի մասին չէ։ Նախ պետք է հասկանալ՝ ձախողումը ծրագրի սպասելի արդյունք է, թե անսպասելի վիճակ։ Այդ որոշումից հետո համապատասխան Elixir գործիքը կիրառելը սովորաբար պարզ է դառնում։

### Փորձեք ինքներդ

Սահմանեք `Registration.validate_age/1` ֆունկցիան, որը թույլատրելի տարիքի դեպքում վերադարձնում է `{:ok, age}`, իսկ մյուս դեպքերում՝ `{:error, :invalid_age}`։ Այնուհետև ավելացրեք `Registration.validate_age!/1` ֆունկցիան, որը վերադարձնում է տարիքը կամ առաջացնում `ArgumentError`։ Փորձեք ձևակերպել, թե ծրագրի որ մասում է հարմար կանչել յուրաքանչյուր տարբերակը։
