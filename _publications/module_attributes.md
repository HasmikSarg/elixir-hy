## Մոդուլի ատրիբուտները (Module attributes)

[Struct-ների մասին հոդվածում](./structs.md) արդեն հանդիպել ենք `@enforce_keys` գրելաձևին։ Այն մոդուլի ատրիբուտ է։ Սակայն `@enforce_keys`-ը մոդուլի ատրիբուտների կիրառության ընդամենը մեկ օրինակ է։ Նույն գրելաձևով Elixir-ը պահում է մոդուլի դոկումենտացիան, ֆունկցիաների նկարագրությունները, compile-time արժեքները և կոմպիլյատորին անհրաժեշտ այլ տեղեկություններ։

Այս հոդվածի նպատակը մոդուլի ատրիբուտների մասին ընդհանուր պատկերացում կազմելն է։ Դրանց ավելի մասնագիտացված կիրառություններին կանդրադառնանք typespec-ների, behaviour-ների և metaprogramming-ի մասին հոդվածներում։

### Ի՞նչ է մոդուլի ատրիբուտը

Մոդուլի ատրիբուտը սահմանվում է մոդուլի մարմնում։ Դրա անվանումը սկսվում է `@` նշանով։

```elixir
defmodule Example do
  @limit 10
end
```

`@limit 10` արտահայտությունը սահմանում է `@limit` ատրիբուտը և դրան տալիս `10` արժեքը։ Իսկ առանց արժեքի գրված `@limit`-ը կարդում է այդ պահին պահված արժեքը։

Կարևոր է մոդուլի ատրիբուտը չշփոթել փոփոխականի հետ։ Այն runtime-ում (ծրագրի աշխատանքի ընթացում) փոփոխվող ընդհանուր վիճակ չէ։ Մոդուլի ատրիբուտների հետ աշխատանքը հիմնականում կատարվում է մոդուլի կոմպիլյացիայի ընթացքում։

Դրանք ունեն երեք հիմնական կիրառություն․

1. մոդուլին կամ ֆունկցիային լրացուցիչ տեղեկություն կցել,
2. կոմպիլյացիայի ընթացքում ժամանակավորապես արժեք պահել,
3. կոմպիլացիայի ժամանակ հաշվարկված արժեքը ներառել ֆունկցիայի կոմպիլացված կոդում։

Դիտարկենք յուրաքանչյուր կիրառություն առանձին։

### Մոդուլի ատրիբուտները որպես նշումներ

Elixir-ն ունի նախապես սահմանված մոդուլի ատրիբուտներ, որոնց նշանակությունը հայտնի է կոմպիլյատորին և այլ գործիքների։ Ամենատարածված օրինակներից են `@moduledoc`-ը և `@doc`-ը։

Պատկերացնենք մոդուլ, որը պատվերի ընդհանուր գումարի նկատմամբ զեղչ է կիրառում։ Այն ստանում է գումարը դրամով և զեղչի տոկոսը։

```elixir
defmodule Store.Pricing do
  @moduledoc """
  Functions for calculating order prices.
  """

  @doc """
  Applies a percentage discount to an order total.
  """
  def apply_discount(total, percent) do
    total - div(total * percent, 100)
  end
end
```

```elixir
iex> Store.Pricing.apply_discount(10_000, 15)
8500
```

`@moduledoc`-ը նկարագրում է ամբողջ մոդուլը, իսկ `@doc`-ը՝ իրեն հաջորդող ֆունկցիան։ Այս տեղեկությունը պահվում է կոմպիլացված մոդուլի հետ։ Այն կարող են կարդալ IEx-ի `h` գործիքը և փաստաթղթեր ստեղծող տարբեր գործիքներ։

Նախկինում օգտագործված `@enforce_keys`-ը նույնպես նախապես սահմանված ատրիբուտ է։ Այն կոմպիլյատորին հայտնում է, թե struct ստեղծելիս որ դաշտերն են պարտադիր։ Հետագայում կհանդիպենք նաև `@spec`, `@behaviour` և `@impl` ատրիբուտներին։ Դրանք տարբեր խնդիրներ են լուծում։

### Ժամանակավոր պահոց կոմպիլյացիայի ընթացքում

Մոդուլի մարմինը կատարվում է կոմպիլյացիայի ընթացքում։ Հետևաբար attribute-ի արժեքը կարող է ստացվել որևէ հաշվարկի արդյունքում։

```elixir
defmodule ExportFormats do
  @formats ["JSON", "CSV", "XML"]
  @normalized_formats Enum.map(@formats, &String.downcase/1)

  def supported_formats do
    @normalized_formats
  end
end
```

```elixir
iex> ExportFormats.supported_formats()
["json", "csv", "xml"]
```

`Enum.map/2`-ը չի կանչվում ամեն անգամ, երբ կանչվում է `supported_formats/0`-ը։ Այն աշխատում է մեկ անգամ՝ `ExportFormats` մոդուլի կոմպիլյացիայի ընթացքում։ Ստացված list-ն այնուհետև ներառվում է `supported_formats/0` ֆունկցիայի կոմպիլացված կոդում։

Սա է մոդուլի ատրիբուտը որպես ժամանակավոր պահոց օգտագործելու իմաստը։ Այս վարքը կարելի է տեսնել նաև attribute-ի արժեքը փոխելու դեպքում։

```elixir
defmodule Limits do
  @limit 10
  def first_limit, do: @limit

  @limit 20
  def second_limit, do: @limit
end
```

```elixir
iex> Limits.first_limit()
10
iex> Limits.second_limit()
20
```

Երկու ֆունկցիաներն էլ runtime-ում (այսինքն ծրագրի աշխատանքի ընթացքում) չեն կարդում ընդհանուր `@limit` պահոցից։ Յուրաքանչյուր ֆունկցիայի կոմպիլացված կոդում ներառված է սահմանման պահին կարդացված արժեքը։ Այս օրինակը բացատրում է աշխատանքի սկզբունքը, սակայն պետք է նշել, որ իրական կոդում նույն ատրիբուտի արժեքը շարունակ փոխելը սովորաբար նվազեցնում է կոդի ընթեռնելիությունը։

### Compile-time արժեքներ

Այլ լեզուներից ծանոթ մոտեցմամբ կարող է ցանկություն առաջանալ յուրաքանչյուր հաստատուն (const) արժեք պահել մոդուլի ատրիբուտում։ Elixir-ում դա անհրաժեշտ չէ։ Սովորական արժեքների համար հաճախ բավական է օգտագործել private ֆունկցիա։

```elixir
defp hours_in_day, do: 24
```

Մոդուլի ատրիբուտը հատկապես օգտակար է, երբ արժեքը պետք է հասանելի լինի կաղապարում կամ guard-ում։ Guard-ի ներսում սովորական private ֆունկցիա կանչել չի թույլատրվում, իսկ compile-time list կամ թիվ կարելի է ներառել attribute-ի միջոցով։

Օրինակ՝ մուտքի քաղաքականության համաձայն հաշիվն արգելափակվում է հինգ անհաջող փորձից հետո։ Ֆունկցիան ստանում է արդեն կատարված անհաջող փորձերի քանակը։

```elixir
defmodule LoginPolicy do
  @max_failed_attempts 5

  def locked?(failed_attempts)
      when is_integer(failed_attempts) and
             failed_attempts >= @max_failed_attempts,
      do: true

  def locked?(_failed_attempts), do: false
end
```

```elixir
iex> LoginPolicy.locked?(4)
false
iex> LoginPolicy.locked?(5)
true
```

Այստեղ `@max_failed_attempts`-ը guard-ի մաս է դառնում կոմպիլյացիայի ընթացքում։ Արժեքի նշանակությունը նաև անմիջապես տեսանելի է նրա անունից, իսկ սահմանաչափը գրված է մեկ տեղում։

### Compile-time և runtime տարբերությունները

Մոդուլի ատրիբուտի արժեքը որոշվում է մոդուլի կոմպիլյացիայի ընթացքում։ Սա կարևոր տարբերություն է հատկապես արտաքին կարգավորումներ կարդալիս։

```elixir
defmodule ServiceConfig do
  @api_url System.get_env("API_URL")

  def api_url, do: @api_url
end
```

Այս տարբերակում `API_URL` միջավայրի փոփոխականը կարդացվում է մոդուլի կոմպիլյացիայի պահին։ Ծրագրի աշխատանքի ընթացքում միջավայրի փոփոխականը փոխելը `api_url/0`-ի պատասխանը չի փոխի։ Նոր արժեք ստանալու համար մոդուլը պետք է կրկին կոմպիլացվի։

Եթե արժեքը պետք է կարդալ հենց runtime-ում, կանչը պետք է կատարվի ֆունկցիայի մարմնում։

```elixir
defmodule ServiceConfig do
  def api_url, do: System.get_env("API_URL")
end
```

Այս տարբերությունը կարևոր է նաև ֆայլերից, տվյալների բազայից կամ արտաքին այլ աղբյուրներից արժեքներ ստանալու դեպքում։ Compile-time հաշվարկը պետք է կիրառել միայն այն ժամանակ, երբ արժեքն իսկապես պետք է որոշվի կոմպիլյացիայի ընթացքում։

### Տարածված սխալներ

Մոդուլի ատրիբուտների հետ աշխատելիս անհրաժեշտ է հիշել մի քանի կանոն։

* Ատրիբուտը սահմանվում է մոդուլի մարմնում։ Այն սովորական global փոփոխական չէ։
* `@name value` գրելաձևը արժեք է սահմանում, իսկ առանձին գրված `@name`-ը փորձում է կարդալ այն։ Չսահմանված ատրիբուտը կարդալիս կոմպիլյատորը զգուշացում է ցույց տալիս։
* Ատրիբուտի անունն ու արժեքը չպետք է բաժանել նոր տողով։ Այդ դեպքում Elixir-ը կարող է արտահայտությունը հասկանալ որպես ատրիբուտի արժեքը կարդալու փորձ։
* Նույն մոդուլի ֆունկցիան հնարավոր չէ կանչել ատրիբուտի արժեքը սահմանելիս։ Այդ պահին մոդուլը դեռ չի կոմպիլացվել, հետևաբար նրա ֆունկցիաները դեռ հասանելի չեն։

### Նեղ մասնագիտացված ատրիբուտներ

Elixir-ի `Module` մոդուլը նկարագրում է բազմաթիվ նախապես սահմանված ատրիբուտներ։ Օրինակ՝ `@spec`-ը նկարագրում է ֆունկցիայի ընդունած և վերադարձրած արժեքների տիպերը, `@behaviour`-ը և `@impl`-ը կիրառվում են behaviour-ների հետ, իսկ `@before_compile`-ը և `@after_compile`-ը կապված են կոմպիլյացիայի փուլերի հետ։ Հնարավոր է ստեղծել նաև սեփական ատրիբուտները։

Այս հնարավորությունները մեկ ընդհանուր հոդվածում մանրամասն ներկայացնելը կպահանջեր դեռևս չուսումնասիրված typespec-ների, behaviour-ների և macro-ների մասին գիտելիքներ։ Դրանց կանդրադառնանք համապատասխան թեմաների հետ միասին։ Առայժմ կարևոր է հասկանալ ընդհանուր սկզբունքը․ Մոդուլի ատրիբուտը մոդուլի compile-time նկարագրության և աշխատանքի գործիք է, ոչ թե runtime-ում փոփոխվող տվյալ։

### Ամփոփում

Մոդուլի ատրիբուտները կարող են՝

* տեղեկություն կցել մոդուլին կամ ֆունկցիային,
* ժամանակավորապես արժեք պահել կոմպիլյացիայի ընթացքում,
* compile-time հայտնի արժեքներ ներառել ֆունկցիաների, կաղապարների և guard-երի մեջ։

Սակայն մոդուլի ատրիբուտ օգտագործելը չպետք է ինքնանպատակ լինի։ Եթե compile-time աշխատանքի անհրաժեշտություն չկա, private կամ public ֆունկցիան հաճախ ավելի պարզ ընտրություն է։

### Փորձեք ինքներդ

Ստեղծեք `PaymentMethods` մոդուլ։ `@supported_methods` attribute-ում պահեք `[:card, :cash, :bank_transfer]` list-ը։ Այնուհետև սահմանեք `supported?/1` ֆունկցիա, որը guard-ի միջոցով կվերադարձնի `true`, եթե ստացած atom-ը list-ում կա, իսկ մյուս արժեքների դեպքում՝ `false`։

Մոդուլին ավելացրեք `@moduledoc`, իսկ ֆունկցիային՝ `@doc`։ Փորձարկեք ֆունկցիան `:card` և `:crypto` արժեքներով։ Վերջում փոխեք `@supported_methods`-ի արժեքը, կրկին կոմպիլացրեք մոդուլը և ստուգեք արդյունքը։
